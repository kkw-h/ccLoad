# ccLoad v4.6.10-beta.2 定制版升级设计

## 目标

以官方 `v4.6.10-beta.2`（commit
`3fbcf9e284e71d3c038ff0680f37551d0d3708e5`）作为新代码基线，重新集成当前线上
`v4.5.0-custom-95ab4d0` 中仍需保留的非 authz 定制能力，产出可验证的
`v4.6.10-beta.2-custom` 源码、Linux amd64 二进制和本地容器镜像。

本轮只完成代码整合、生产 PostgreSQL 数据库副本迁移测试和本地构建，不修改生产
数据库、不替换线上二进制、不重启线上 ccLoad 或 CPA。

## 升级策略

采用“官方 beta 新基线 + 按功能重新移植”的方式：

1. 从不可变标签 `v4.6.10-beta.2` 创建独立升级分支和 worktree。
2. 不把当前定制分支整体 merge 到 beta，也不直接连续 cherry-pick 全部旧提交。
3. 逐项比较旧实现与 beta 重构后的接口，在 beta 架构上恢复定制行为及测试。
4. 每个定制能力独立提交，便于审查、定位回归和后续跟随上游升级。
5. 官方 beta 的 OAuth、Codex、Antigravity、xAI、WebSocket、错误分类和协议转换行为
   作为新基线保留；只有与本地安全边界或线协议契约冲突时才做最小适配。

不采用以下方案：

- 直接部署官方 `ghcr.io/caidaoli/ccload:v4.6.10-beta.2`，因为会关闭现有用量事件链路，
  且缺少多 Token 日志、管理 OpenAPI 和本地 PostgreSQL 兼容修复。
- 将当前分支直接 merge 到 beta，因为双方在代理、存储、设置、WebSocket 和前端
  文件上存在大范围重构，机械冲突解决难以证明行为完整。

## 必须保留的定制能力

### authz 范围边界

- 本次升级不包含外部 authz、`X-Sedna-Env` 环境选择、外部鉴权环境表或管理后台。
- `/v1`、`/v1beta`、Codex HTTP 和 Responses WebSocket 保持官方 beta 的本地 Token
  鉴权链路，不额外调用 authz。
- 升级分支中已经引入的 authz 提交必须使用独立 revert 提交完整撤销，便于审计。
- Redis 用量事件的 environment 仅从最终本地 Auth Token 描述中提取，不依赖 authz。

### Redis 用量事件与 499 计费

- 保留可选 Redis Publisher；未配置 Redis 时为 fail-open 的 NoopPublisher。
- attempt 事件继续以成功落库的日志为事实来源，request 事件作为请求级汇总。
- 用量事件按最终 Token 的 environment 路由到对应 stream 或 channel。
- 499 客户端取消但已获得 usage 时继续计费并发布实际 usage，不计入成功/失败健康度。
- Redis 不可用、缓冲区满或发布失败不得影响代理响应。

### 管理和兼容能力

- 日志及统计查询继续支持多个 `auth_token_id`，并保持单值查询兼容。
- 保留 `/docs/` Swagger UI 和 `/docs/openapi.yaml` 管理 API 文档；文档需要补充 beta
  新增管理接口，不能只恢复旧文件。
- 保留 PostgreSQL `models.disabled` 以整数参数写入 `int2` 字段的编码修复，并增加
  PostgreSQL 回归测试。
- 保留非流式协议超时设置，包括全局 `non_stream_timeout` 以及 Anthropic、Codex、
  OpenAI、Gemini 的协议级覆盖；现有数据库值（线上为 300 秒）不得被迁移重置。

## 上游协议核心

beta 标签已经包含比当前定制分支更新的 `internal/protocol/cliproxy` 快照。升级时以 beta
标签中的 `UPSTREAM.md`、生产源码和同步测试为整体，不从旧定制分支覆盖协议目录。

整合完成后执行协议快照确定性审计，并确认以下 ccLoad Registry 契约仍成立：

- 请求转换失败返回客户端 400，不触发渠道切换或冷却。
- reasoning、signature、tool call、usage 和 SSE 终止帧保持 Registry 测试定义的形状。
- 不引入 CLIProxyAPI 的认证、路由、配置、插件或运行时 Go module 依赖。

## 数据库迁移验证

迁移测试只针对生产 PostgreSQL 的副本进行，过程如下：

1. 通过现有 SSH 隧道或 PostgreSQL 工具创建生产库的一致性逻辑备份；备份文件放在
   临时目录，不进入仓库。
2. 创建独立的本地或临时 PostgreSQL 数据库，禁止使用生产 DSN。
3. 将备份恢复到测试数据库，记录恢复前 schema、关键表行数和设置值。
4. 使用 custom beta 二进制连接测试数据库并执行一次完整启动迁移。
5. 重启同一二进制再次启动，验证迁移幂等。
6. 验证 OAuth 新字段和表可用，同时确认 Auth Token、渠道/模型、日志查询数据和协议级
   非流式超时未丢失或被重置。
7. 对迁移后数据库执行模型 disabled 保存和多 Token 日志查询。
8. 测试结束后停止测试实例；不自动删除备份，保留其路径和 SHA-256 供人工确认。

如果无法取得生产库副本，数据库阶段判定为未完成，不能用空库迁移测试替代，也不能
将构建成功描述为具备上线条件。

## 测试与构建

代码整合至少通过以下验证：

1. 定制能力定向测试：Redis usage、environment stream 路由、499 计费、多 Token 日志
   过滤、OpenAPI、PostgreSQL disabled 编码和超时。
2. `go test -tags sonic ./internal/...`。
3. `make verify-web`。
4. 协议快照审计脚本及 Registry 边界测试。
5. `golangci-lint run ./...`。
6. `make build` 和 `git diff --check`。
7. 构建 Linux amd64 静态二进制，版本字符串包含
   `v4.6.10-beta.2-custom-<short-sha>`。
8. 使用仓库 release Dockerfile 构建本地镜像，并在临时 PostgreSQL 副本上完成启动、
   `/health`、`/public/version`、`/docs/openapi.yaml` 和管理接口冒烟测试。

并发代理或 WebSocket 相关移植影响共享状态时，额外执行 `make race-fast`；如果定向 race
测试暴露更广范围风险，再执行完整 `make race`。

## 验收标准

本轮完成必须同时满足：

- 升级分支明确基于官方 `v4.6.10-beta.2` commit。
- 所有必须保留的定制能力都有实现和自动化回归测试。
- beta 新增 OAuth、WebSocket 和错误分类测试未因定制移植退化。
- 完整 Go 测试、Web 测试、lint、协议审计和构建均退出码为 0。
- 生产数据库副本完成首次迁移、二次启动和定制定向数据验证。
- 生成 Linux amd64 二进制、本地镜像标识、SHA-256 和验证记录。
- 生产服务、生产数据库和线上 CPA 未发生变更。

任何一项未满足都只报告实际完成范围，不进入生产部署阶段。

## 后续上线边界

生产部署不属于本规格。后续如果用户明确要求部署，需要单独制定上线计划，至少包含
生产数据库备份、低峰灰度、Redis consumer 积压观察、旧二进制和数据库回滚点，以及
597/598/599 和 WebSocket 指标监控。
