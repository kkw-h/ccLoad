# ccLoad 模型推理强度发现设计

日期：2026-08-09

## 目标

让客户端通过 `GET /v1/models` 获得每个公开模型可用的推理强度。能力由该公开模型在渠道配置中的 `redirect_model`（原模型名）决定，并允许管理员按原模型名称进行全局人工覆盖。

示例：

```text
sciland-3.0 → redirect_model: gpt-5.6-sol
              → [low, medium, high, xhigh]
```

本功能只发布能力元数据，不修改、补全、拒绝或降级客户端请求中的推理强度；现有协议转换和请求转发行为保持不变。

## 当前状态

- 渠道模型条目只有 `model`、`redirect_model` 和 `disabled`。
- `GET /v1/models` 的 OpenAI/Codex 形态只返回 `id`、`object`、`created` 和 `owned_by`。
- 同一路径在 Anthropic 客户端下返回 `id`、`display_name`、`type` 和 `created_at`。
- ccLoad 协议核心已经识别 `none`、`minimal`、`low`、`medium`、`high`、`xhigh` 和 `max`，但尚无面向模型列表的能力注册表。
- 生产配置中 `sciland-3.0` 映射到 `gpt-5.6-sol`。

## 方案

采用“内置能力注册表 + 全局人工覆盖 + `/v1/models` 增量字段”。不增加独立数据库表；人工覆盖持久化为系统设置，使其能够通过现有设置服务动态生效。

未采用以下方案：

- 独立能力接口：会要求客户端额外请求，不能满足模型列表直接发现能力的目标。
- 动态探测上游：多数上游没有稳定的能力接口，探测结果不可作为可靠契约。

## 规范化推理强度

允许值和固定返回顺序为：

```text
none, minimal, low, medium, high, xhigh, max
```

人工配置必须使用上述值。保存时转为小写、去重并按固定顺序排列；出现未知值时整个更新返回 HTTP 400，不进行部分保存。

## 内置能力注册表

后端新增单一职责的能力解析组件。首个必须包含的精确映射为：

```json
{
  "gpt-5.6-sol": ["low", "medium", "high", "xhigh"]
}
```

注册表使用归一化后的原模型名进行精确匹配：去除首尾空格并转为小写。不根据相似名称猜测能力，避免未来同系列模型能力变化导致错误声明。后续内置模型通过代码和测试显式增加。

## 全局人工覆盖

新增系统设置：

```text
model_reasoning_effort_overrides
```

值为 JSON 对象，键是原模型名，值是推理强度数组：

```json
{
  "gpt-5.6-sol": ["low", "medium", "high", "xhigh"],
  "custom-reasoner": ["none", "high"]
}
```

覆盖规则：

1. 原模型存在人工配置时，使用人工配置。
2. 否则使用内置能力注册表。
3. 两者均不存在时，该原模型能力为“未知”。
4. 人工配置为空数组表示明确不支持可选择的推理强度，不回退内置值。
5. 删除某项人工配置后立即恢复内置判断。

设置校验限制为最多 500 个原模型，每个模型名为 1–255 个非空字符，防止异常配置无限增大请求处理成本。

## 公开模型解析

对 Token 当前可见的每个公开模型：

1. 先沿用现有 Token 模型限制、渠道限制、渠道启用状态和模型禁用状态筛选候选渠道。
2. 找到渠道中的同名 `ModelEntry`。
3. `redirect_model` 非空时将其作为原模型名，否则使用 `model` 本身。
4. 使用“人工覆盖优先、内置注册表兜底”解析原模型能力。
5. 一个公开模型只有一个已知原模型时，直接使用该能力集合。
6. 同一公开模型可路由到多个不同原模型时，所有原模型能力均已知才返回交集；任一原模型能力未知时省略能力字段。
7. 交集为空时返回空数组，明确表示没有跨所有候选渠道都安全可用的共同强度。

该规则确保返回的强度不会因实际路由到另一个候选渠道而失效。

## API 响应

OpenAI/Codex 形态在单个模型对象上新增可选字段：

```json
{
  "id": "sciland-3.0",
  "object": "model",
  "created": 0,
  "owned_by": "system",
  "supported_reasoning_efforts": ["low", "medium", "high", "xhigh"]
}
```

Anthropic 形态使用相同的 `supported_reasoning_efforts` 字段：

```json
{
  "id": "sciland-3.0",
  "display_name": "Sciland 3.0",
  "type": "model",
  "created_at": "1970-01-01T00:00:00Z",
  "supported_reasoning_efforts": ["low", "medium", "high", "xhigh"]
}
```

语义约定：

- 能力未知：省略 `supported_reasoning_efforts`。
- 明确没有共同强度：返回 `supported_reasoning_efforts: []`。
- 不向客户端暴露 `redirect_model` 或渠道信息。
- 顶层响应结构和现有字段保持不变。

`GET /v1beta/models` 的 Gemini 形态不在首期范围内，避免将未确认的非标准字段同时扩展到另一个协议。

## 管理后台

在系统设置的高级区域增加“原模型推理强度覆盖”编辑器：

- 原模型名称输入框。
- 七个规范化推理强度的多选控件。
- 添加或更新覆盖项。
- 删除覆盖项并恢复自动判断。
- 保存前在浏览器端执行与后端一致的基础校验，后端仍是最终校验权威。

界面只编辑人工覆盖项；内置注册表不复制到前端，避免前后端能力表漂移。保存继续使用现有管理员设置更新链路，不新增未鉴权接口。

## 数据流与缓存

能力解析器复用 ConfigService 的设置快照。内置注册表是只读数据；人工覆盖 JSON 在设置加载或更新时解析为不可变映射。`/v1/models` 请求只执行映射查询和小集合交集，不访问上游，也不为每个模型额外查询数据库。

设置更新成功后通过现有配置刷新机制对后续请求生效，不要求重启 ccLoad。

## 错误处理

- 设置 JSON 不是对象、模型名非法、强度不是字符串数组或包含未知强度：HTTP 400。
- 配置超过数量限制：HTTP 400。
- 运行时遇到历史脏配置：记录一次受限警告，忽略整份人工覆盖并使用内置注册表，不能让 `/v1/models` 返回 500。
- 渠道配置读取失败：保持现有 `/v1/models` 错误行为。

## 兼容性与安全

- 新字段为增量 JSON 字段，现有顶层和模型基础字段不变。
- 只根据当前 Token 可见的候选渠道计算能力，不能借此推断无权限渠道。
- 不返回真实上游模型名、渠道名或渠道 ID。
- 不改变 authz；本项目当前取消的外部 authz 业务不在本功能范围内。
- 不改变请求体推理参数或计费逻辑。

## 测试与验收

后端单元测试：

- `gpt-5.6-sol` 内置映射返回 `low/medium/high/xhigh`。
- 人工覆盖优先于内置映射，删除后恢复内置映射。
- 空数组覆盖、未知模型、非法强度、重复值、大小写和固定排序。
- 多原模型取交集；存在未知原模型时省略字段；空交集返回空数组。
- Token 模型限制和渠道限制不会泄露不可见渠道能力。

Handler 测试：

- OpenAI、Codex 和 Anthropic `/v1/models` 响应包含正确字段。
- 未知能力省略字段，明确空集合保留空数组。
- 现有 `object/data/first_id/last_id/has_more` 结构不变。

设置和前端测试：

- 合法覆盖可以保存并动态生效。
- 非法 JSON、非法模型名、未知强度和超限配置被拒绝。
- 管理后台可添加、更新、删除覆盖项并正确序列化。

回归验证：

- `go test -tags sonic ./internal/...`
- `make verify-web`
- `golangci-lint run ./...`
- `git diff --check`
- 使用 `sciland-3.0 → gpt-5.6-sol` 做线上部署前副本冒烟，确认返回四档推理强度。

## 非目标

- 不自动探测上游能力。
- 不在首期扩展 Gemini `/v1beta/models`。
- 不校验或拒绝客户端实际提交的推理强度。
- 不根据模型名模糊猜测能力。
- 不新增渠道级或公开模型级人工覆盖。
