# ccLoad v3.14 定制版升级设计

## 目标

将 YiSuo 中转站上的 ccLoad 从 `v3.13.3-custom-ce0604f` 升级到基于官方
`v3.14.0` 的定制版本，同时完整保留现有 `X-Sedna-Env` 外部鉴权能力。

## 基线与范围

- 定制功能基线：`origin/master` 的 `ce0604f`。
- 官方升级目标：标签 `v3.14.0`，提交 `7b91806`。
- 不修改 `medge-ai-api`。
- 不改变现有 PostgreSQL 数据、systemd 服务参数或外部鉴权配置。

## 集成方式

在隔离分支 `kkw/upgrade-v3.14-custom` 中，将官方 `v3.14.0` 合并到
`ce0604f`。冲突处理以保留两侧行为为原则：

- 保留定制版的外部鉴权数据库、管理界面和代理中间件。
- 接收 v3.14.0 的 Responses WebSocket 生命周期增强、服务等级倍率显示修复，
  以及 v3.13.2 至 v3.13.4 的全部修复。
- 版本字符串使用 `v3.14.0-custom-<commit>`，确保管理界面和健康检查可辨识。

## 验证

构建前运行依赖下载与基线测试。合并后至少执行：

- Go 全量测试。
- Web 前端测试。
- Linux amd64 生产构建。
- 本地启动后的健康与版本检查。
- 外部鉴权关键测试，覆盖开关关闭、环境匹配、未知环境、绕过 CIDR 和返回
  ccLoad Token 后继续本地权限校验。

## 部署与回滚

部署前在服务器保留带时间戳的当前二进制备份。上传新二进制后原子替换并重启
`ccload.service`，检查：

- systemd 状态为 `active`。
- `/health` 返回 HTTP 200。
- `/public/version` 返回 `v3.14.0-custom-*`。
- 代理和外部鉴权路径行为符合现有配置。

如果服务无法启动或关键检查失败，立即恢复备份二进制、重启服务并重新验证健康
状态。

## 风险

主要风险是官方 WebSocket 路由改动与定制外部鉴权中间件的组合。通过合并冲突
审查、定向测试和部署后鉴权验证控制风险。数据库迁移由 ccLoad 启动流程执行，
部署前不手工修改生产数据。
